**Date analyzed:** 2026-08-17

## 1. Summary

**Title:** Multitask Ranking System for Immersive Feed and No More Clicks: A Case Study of Short-Form Video Recommendation
**Authors:** Qingyun Liu, Zhe Zhao, Liang Liu, Zhen Zhang, Junjie Shan, Yuening Li, Shuchao Bi, Lichan Hong, Ed H. Chi (Google DeepMind / Google Inc.)
**Venue/Year:** CIKM 2023

**Abstract (paraphrased):** Short-form video (SFV) platforms use an "immersive feed" UI that auto-plays one video at a time instead of presenting users a set of choices to click. This removes the click signal that conventional recommenders rely on both for engagement labels and for correcting click-based position bias, and it worsens label sparsity/skew for behaviors like commenting and sharing (which post-click recommenders can otherwise densify by filtering non-click impressions). The paper introduces a unified multi-task ranking framework with two novel components addressing these SFV-specific challenges: (1) correction for a newly identified "watch trail" bias (analogous to position bias, but defined over the sequence of consecutive video watches rather than a list of clickable results), and (2) a disentangle regularization plus sparse-task-upweighting plus meta-learning-based weight-selection strategy to reduce task conflict when co-training extremely sparse and dense behavior tasks together.

**Key contributions:**
1. Identification and analysis of "watch trail bias" — a new source of system bias specific to click-free immersive feeds, measured via relative movement of user behaviors along the trail position for randomly-promoted videos.
2. A learnt bias-correction term (a shallow "debias tower" over trail-related, non-serving-time features) added as a regularizer to each task's logits.
3. A disentangle regularization (Frobenius-norm penalty on inter-expert Pearson correlation of MMoE's latent expert representations) to reduce task conflict in a shared MMoE backbone when co-training tens of tasks.
4. Loss upweighting for extremely sparse tasks, plus a meta-learning algorithm (a learned model "G") that predicts the combined live-metric impact of a candidate upweighting value, avoiding expensive live-experiment grid search for weight selection.

**Methodology:** Candidates from an upstream retrieval stage (a few hundred per request) are scored by an MMoE-based multi-task ranking model. Input features (candidate/video, query/watch-history, context/device+demographics) go through a shared bottom layer, then MMoE (shared experts + per-task gating networks), then per-task towers producing classification (e.g., like/dislike, comment) or regression (e.g., watch duration) predictions. Task predictions are combined via a manually-tuned-or-learned **weighted multiplication** into the final ranking score at serving time. Training data is generated chronologically from user logs (models trained sequentially on earlier-to-later days; same-day samples shuffled). Point-wise losses are used throughout for serving efficiency. The overall training loss is L_model = L_dense + Σ w_i·L_i (over sparse tasks), plus λ·L_reg (the disentangle regularization term).

**Main results:** Watch-trail bias correction applied to all tasks: **+1.96% Overall Enjoyment** (live metric) versus a model without bias correction; applying it to a single task still improves that task's own metrics but the largest gain comes from applying to all tasks. Disentangle regularization: up to **+0.33% Overall Enjoyment** and up to **+1.32% Classification Task Metric** / **+0.67% Regression Task Metric** at the best-tuned λ. Sparse-task upweighting in co-training (vs. training sparse tasks separately): **+0.29% Overall Enjoyment** and up to **+6.61%** on sparse-task-specific live metrics at upweight=1000 (with dense-task metric degrading up to −1.13% at that extreme), showing an explicit sparse-vs-dense trade-off curve. The meta-learned weight-selection strategy achieves live performance comparable to an expensive handpicked (grid-searched) weight while using far less training/live-experiment data for selection.

## 2. Experiment Critique

- **Design:** The paper separately ablates each of its three contributions (trail-bias correction, disentangle regularization, sparse-task upweighting) against a clearly defined Control in each case, which is methodologically clean and lets each component's marginal contribution be read independently.
- **Statistical validity:** Live-experiment tables mark results with an asterisk for "significant at 95% Confidence Interval," and this convention is used consistently (e.g., Table 1, Table 2, Table 4). Offline results are reported via AUC (classification) and RMSE (regression) but specific offline numbers/deltas are largely omitted from the reviewed pages ("offline experiments... we omit for brevity" for one figure); the paper leans more heavily on live-experiment evidence than offline benchmark tables.
- **Online experiments:** All headline results (Tables 1, 2, 4, and Table 3 for meta-learned weight selection) are live A/B tests, with a portion of real traffic diverted to control/treatment over 2+ weeks — a real, non-trivial online evaluation, and the framework has been in production for more than 6 months at the time of writing.
- **Reproducibility:** Not reproducible externally — evaluated on a proprietary platform described only as "one of today's largest SFV platforms" (not named explicitly in the reviewed pages, though the CCS concepts, author affiliation with Google DeepMind/YouTube Shorts-adjacent work, and framing strongly suggest a Google-operated SFV surface); no dataset or code release. A synthetic dataset (1M examples, one dense + one sparse task) is used specifically to benchmark imbalance-learning strategies in a controlled, reproducible setting (Section 5.1/Figure 4), which is a methodological strength for that sub-comparison.
- **Limitations/negative results stated by authors:** The meta-learned weight-selection method (Sec 6.3.3) is explicitly limited to selecting a *single, unified* upweighting value that cannot be customized per sparse task. The abstract itself frames "sources of system biases under the new [immersive-feed] UI" as "yet unexplored" beyond what this paper covers, i.e., the trail-bias treatment is presented as a first step, not a complete bias-correction solution.

## 3. Industry Contribution

- **Deployability:** The framework "has been deployed to the production system for more than 6 months" at the time of the paper, across tens of co-trained tasks, on a platform with "tens of billions of user interactions" over "millions of items" — a strong, concrete deployment claim with a stated retention duration.
- **Problems solved:** Solves two SFV-specific engineering problems that break the standard click-based recommender-system playbook: (1) no click-based position bias exists in a click-free immersive feed, requiring a new bias model (watch trail); (2) co-training extremely sparse behavior tasks (comment/share, label mean as low as 1e-5) with dense tasks (watch) causes severe negative transfer, addressed via disentangle regularization and adaptive upweighting rather than separate single-task models.
- **Engineering cost:** The debias tower is a lightweight shallow network added on top of existing task logits at training time (with 10% dropout on trail features to reduce train/serve skew, since trail features are non-serving/label-adjacent). The meta-learning weight-selection approach is explicitly engineered to be cheaper than live-experiment grid search — it "saves iteration time" and uses less data (as little as 20% of log data) to select comparable weights, which is a direct operational-cost saving for iteration speed on a live-serving system.
- **Ranking pipeline framing:** This is a main ranking-stage model (post-retrieval, scoring "a few hundred candidates"), fitting cleanly into the standard retrieval → ranking industrial pipeline; the paper explicitly cites the standard multi-stage pipeline pattern (YouTube, Google Play, Facebook, Pinterest) as its architectural starting point.

## 4. Novelty vs. Prior Work

Novelty is framed relative to (a) the standard MMoE multi-task ranking backbone (Ma et al. 2018, and the closely related "Recommending what video to watch next" multitask ranking system, Zhao et al. 2019, cited as the direct architectural predecessor), which the paper augments rather than replaces; (b) prior position-bias correction work, which the paper argues is inapplicable because it is defined for click-based systems, motivating the new "watch trail" bias concept as an SFV-specific analogue; (c) prior imbalance-learning and multi-task-weighting literature (Gradnorm, Uncertainty Reweighting, Focal Loss, disentangle/decorrelation regularization from "Multi-Task Causal Representation Learning" — note this cited "causal" work is about disentangling *representations*, not about causal effect estimation), which the paper adapts specifically for the extreme sparsity regime (label means as low as 1e-5) found in SFV behavior signals, and augments with a novel meta-learning weight-selection step the paper claims is new for efficiently avoiding expensive live-experiment grid search at this scale.

## Project Relevance

Speaks to **Q4** (fusion of short-term event heads: an MMoE backbone plus a learned/manual weighted-multiplication combination, plus a disentangle regularizer specifically designed to reduce cross-task interference among sparse and dense tasks — directly relevant given the project's own low-base-rate cascade) and, secondarily, to **Q6** (a documented, cheaper meta-learning alternative to expensive live-experiment grid search for choosing task weights, which is relevant to how the project might efficiently tune fusion weights online). It does **not** address Q1, Q2, Q3, Q5, Q7, or Q8 — there is no long-horizon objective, no delayed label, no credit-assignment mechanism beyond single-impression, no incrementality, and no two-sided-market treatment. As the batch note anticipated, "no clicks" here is replaced by other *immediate* passive-engagement signals (watch, like, comment, share), not by any multi-day retention or revenue proxy — this paper's departure from CTR-style proxies is about UI-forced signal substitution, not about moving to a longer-horizon objective, which is a materially different move from what the project needs.
